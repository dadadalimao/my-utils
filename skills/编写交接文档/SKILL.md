# 项目交接文档编写

## 目标

帮助接手人员在 **1–2 天内独立跑通环境、找到资源、理解核心业务**，而不是只写功能清单。

**平衡两类内容：**
- **工程实操**：仓库地址、环境 URL、配置来源、启动方式、部署回滚、账号获取方式
- **业务知识**：核心流程、状态机、定时任务、关键接口（按项目复杂度取舍）

## 编写流程

```
1. 扫描代码库 → 2. 按模板起草 → 3. 对照检查清单补漏 → 4. 标注「待确认」项
```

### Step 1：扫描代码库（必做）

在写文档前，从仓库中提取事实，避免路径/配置写错：

| 检查项 | 常见位置 |
|--------|----------|
| 技术栈与版本 | 根 `build.gradle` / `package.json` / `pom.xml` |
| 模块结构 | `settings.gradle`、目录树 |
| 启动类与端口 | `*Application.java`、`application*.properties` |
| Profile 机制 | `spring.profiles.active`、`*-{env}.properties` |
| 数据库迁移 | `db/migration/`、Flyway/Liquibase 配置所在模块 |
| CI/CD | `.drone.yml`、`.github/workflows/`、Jenkinsfile |
| 第三方配置 | properties、环境变量、`sys_constant` 等运行时配置 |
| 定时任务 | `@Scheduled`、xxl-job 等 |
| 敏感文件位置 | 证书、密钥、`.env`（只写路径，不写内容） |

**原则：** 文档中的路径、库名、部署方式必须与代码一致；不确定的写 `{待确认}` 并注明需问谁。

### Step 2：按模板撰写

使用 [template.md](template.md) 作为章节骨架。完整模板见该文件。

**章节优先级（时间紧时）：**

1. **必写**：1 文档说明、2 项目简介、3 人员与交接范围、7 项目结构、10 环境启动、11 部署运维、12 账号安全、**关键资源获取索引**
2. **强烈建议**：4 技术栈、8 数据库、9 第三方服务、13 日志排障
3. **按业务复杂度**：5 功能概览、6 核心业务流程（复杂系统重点写状态机/定时任务/关键接口）

### Step 3：对照检查清单

完成后逐项核对 [checklist.md](checklist.md)。空白表格、空链接、只写工具名不写 URL 视为未完成。

### Step 4：输出规范

- 语言：中文（除非项目明确要求英文）
- 格式：Markdown，章节用 `## 1.` 编号，表格承载元信息
- 敏感信息：**禁止**写入密码、Token、私钥；写「存放位置 + 获取方式 + 负责人」
- 空字段：写 `{待补}` 或 `{待确认}`，不要留空表格行
- 版本：文档头部记录版本号与更新日期

## 关键资源获取索引（每份交接文档必须有）

单独一节或在 12 章汇总，格式如下：

```markdown
## 关键资源获取索引

| 资源 | 地址/位置 | 获取方式 | 负责人 |
|------|-----------|----------|--------|
| 后端仓库 | https://... | GitHub 权限找 xxx | |
| 前端仓库 | {待补} | | |
| 接口文档 | Apifox 项目链接 | 邀请加入 | |
| Bug 系统 | Redmine/Jira URL | 账号申请找 xxx | |
| CI 平台 | Drone/Jenkins URL | | |
| 测试账号 | — | 找 xxx 开通 | |
| 生产/测试 URL | 见 11.1 | — | |
```

## 配置来源说明（易遗漏，必须写清）

很多项目配置不在单一 properties 文件里。文档需列出**所有配置来源**：

| 来源类型 | 示例 | 文档写法 |
|----------|------|----------|
| 配置文件 | `application-dao-prod.properties` | 路径 + 对应 profile |
| 数据库常量表 | `sys_constant` | 表名 + 后台管理入口 + 典型 key |
| 代码硬编码 | 支付类、SDK 初始化 | 文件路径（提醒改造风险） |
| 证书/密钥文件 | `apiclient_key.pem` | 目录 + 获取方式 |
| CI Secrets | Drone `from_secret` | Secret 名称 + 维护平台 |
| 运行时覆盖 | pm2、K8s env | 启动命令或 manifest 位置 |

## 核心业务流程章节（第 6 章）写法

复杂业务项目可参考沃飞宠物文档，包含：

1. **模块/服务架构图**（ASCII 或 mermaid）
2. **状态机**：状态列表 + 转换规则表 + 触发条件（接口/定时任务）
3. **关键定时任务表**：类名、Cron、功能、是否启用
4. **核心接口速查**：路径、方法、状态变更
5. **数据表关系**（主表及关联）
6. **并发/一致性要点**（锁、快照、回调验签等）

简单 CRUD 项目可压缩为「主流程 1–3 条 + 关键表」。

## 审查已有交接文档

用户要求审查时，输出结构：

```markdown
# 交接文档审查报告

## 总体结论
[业务覆盖 vs 工程实操，一句话]

## 完全缺失（阻塞接手）
- ...

## 与代码不一致（会误导）
- 文档写法 → 实际代码位置

## 建议补充的获取方式
| 缺失项 | 建议写法 |

## 已覆盖且质量较好
- ...
```

审查时必须对照代码库验证路径、部署方式、Profile、迁移脚本位置。

## 反模式（禁止）

- 只写功能列表，不写「去哪拿账号/密钥/文档」
- 部署写「Docker」但实际是 jar + pm2（需与 CI 脚本一致）
- Flyway/迁移脚本路径写错模块
- 第三方配置只指向 properties，忽略 DB 常量表或硬编码
- 留空表格假装已交接（「确认」但无 URL/联系人）
- 把生产密码写进文档
