# 本项目网文去味

以 `story-deslop` 的表达、用笔、故事三层方法诊断并修订正文，但必须服从本项目的
章节结构、导出目录和提示词。目标是让文字自然、叙事有重心、行为有依据；不追求
固定句式、标点或检测器分数。

## 开始前

1. 从工作目录定位 Git 仓库根。所有项目路径均相对仓库根。
2. 只要准备依据应用提示词改写，先运行：

   ```powershell
   node .cursor/skills/story-deslop-app/scripts/check-prompt-sync.cjs
   ```

   退出码非 0 时，不要使用任何一份模板改写正文。向用户报告不一致的常量，修复后
   再继续。客户端
   `apps/mini/apps/client/src/constants/templates.ts` 是运行时基准；服务端
   `apps/mini/apps/server/prisma/seed.ts` 中同名提示词必须与它逐字一致。
3. 确定范围和文风。优先读取：

   - `exports/{用户名}/{书名}/书籍.md`
   - `exports/{用户名}/{书名}/设定/本书设定.md`
   - 本次章节、相邻章节、对应章纲和全书大纲中与本次修改直接相关的部分

   用户、本书设定和当前所选模板的明确要求优先于通用去味规则。不要擅自把一种
   文风套到所有作品上。

需要导出或回写时，先完整读取并遵循
[`../novel-md-sync/SKILL.md`](../novel-md-sync/SKILL.md)。`GET` 会清空该书导出目录；
目录中有未保存的本地修改时，不要自动重新导出。只有用户明确要求“回写”或“上传”
时才调用 `POST`。

## 工作模式

- “诊断 / 看看哪里像 AI / 先别改”：只报告问题、位置、阅读后果和最小改法，
  不修改正文。
- “去 AI 味 / 改写 / 润色”：修改用户指定的导出章节文件，逐章处理；默认不就
  全书写长篇报告，也不自动回写数据库。
- “去味并回写 / 上传”：完成修改和复核后，按 `novel-md-sync` 只回写当前这一本。

作者未指定范围时，按完整章节检查三层；作者只提出某类问题时，缩小检查范围。

## 三层处理

先读 [references/diagnosis.md](references/diagnosis.md)，按其中定义执行。

1. 表达：处理电报体、机械并列、模板词、套式声口和无功能微动作；保留作者本来
   有效的直写、停顿、短句和口语。
2. 用笔：检查场景作用、详略、关键过程、细节功能、情绪承接和章末信息交付；
   删除、压缩或展开都要说明依据。
3. 故事：检查行为依据、因果、人物立场、手段与结果、变化承接、知情顺序。

故事层问题只有在能够由原文已有信息核实并恢复承接时才直接修。改变事件、动机、
关系、胜负、代价、人物知识或伏笔顺序时，先给最小设计方案、影响范围和需要用户
决定的事项。未获授权不要改。

不要把去味理解成强制加入脏话、闲笔、肢体动作、玩梗、电影镜头或私人经历。
这些素材只有符合本书人物、场景和作者要求时才能使用。不要机械清零破折号、
统一引号、规定对话占比或追求某种标点节奏。

## 改写规则

- 保留剧情事实、时间线、人物选择、因果、视角、信息边界和章节目标。
- 保留本书已建立的人物声口；无法确认的声口从相邻场景和本书设定推断，仍无法
  判断时保留原表达或标为待确认。
- 先改可独立确认的表达与详略，再处理需上下文的句子；故事依据不足时不要用
  微动作或总结句掩盖缺口。
- 只改指定章节；不要顺手重写全章或后文。
- 修改导出文件后，至少回读一次改动处的场景，核对事实、人物知识、空间方向、
  情绪承接和悬念是否保持。

## 交付

诊断只输出三层发现、可定位原文、阅读问题和建议，不输出改写正文。

改写后输出：

- 已修改文件和具体段落的简短说明
- 表达、用笔、故事三层分别处理了什么
- 仍需剧情设计授权或资料不足的部分
- 少量有代表性的前后对照

不要宣称通过任何 AIGC 检测器；检测分数不是验收标准。
